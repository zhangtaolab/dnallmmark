## Warnings

### WR-01: Error-bar plugin's vertical-bar branch draws wrong geometry (latent)

**File:** `dnallm-mark/js/error-bars.js:119-135`
**Issue:** In bar-cap mode the constant-axis anchor is unconditionally
`el.y` and caps/stems are stroked with the value-axis pixels as the first
(x) coordinate. For a horizontal chart (`indexAxis: 'y'`, the task page)
this is correct. But the branch explicitly claims vertical support by
selecting `chart.scales.y` as the value scale when `indexAxis !== 'y'`
(line 120) — and for a vertical bar, `el.y` lies on the **value** axis, not
the category axis, so the anchor must be `el.x` and the `moveTo/lineTo`
coordinate order transposed. Verified by executing `afterDatasetsDraw`
against a mock chart: for a vertical bar with whisker values 0.3/0.7 the
plugin emits horizontal strokes at `y=100` from `x=60..140` instead of
vertical strokes at the bar's `x` from `y=60..140`. The clamp bounds
(lines 124-125) are also hardcoded to `[chartArea.left, chartArea.right]`,
which is the wrong axis pair for the vertical case. Both shipped charts
(horizontal bars + scatter) never reach this path, and the phase plan
(17-02-PLAN Task 1) specified the same shape — but this is a generic
reusable plugin whose orientation dispatch exists precisely for this case;
the first vertical-bar consumer gets garbled whiskers.
**Fix:**
```js
if (Array.isArray(raw)) {
  if (raw.length !== 2 || raw[0] === raw[1]) return;
  const horizontal = chart.options.indexAxis === 'y';
  const valueScale = horizontal ? chart.scales.x : chart.scales.y;
  if (!valueScale) return;
  const g = whiskerGeometry(
    horizontal ? el.y : el.x, raw[0], raw[1], valueScale, options.capWidth
  );
  if (!isFinite(g.lo) || !isFinite(g.hi)) return;
  if (horizontal) {
    const lo = clampPixel(g.lo, chartArea.left, chartArea.right);
    const hi = clampPixel(g.hi, chartArea.left, chartArea.right);
    ctx.beginPath();
    if (options.drawStem) { ctx.moveTo(lo, g.anchor); ctx.lineTo(hi, g.anchor); }
    ctx.moveTo(lo, g.anchor - g.capHalf); ctx.lineTo(lo, g.anchor + g.capHalf);
    ctx.moveTo(hi, g.anchor - g.capHalf); ctx.lineTo(hi, g.anchor + g.capHalf);
    ctx.stroke();
  } else {
    const lo = clampPixel(g.lo, chartArea.top, chartArea.bottom);
    const hi = clampPixel(g.hi, chartArea.top, chartArea.bottom);
    ctx.beginPath();
    if (options.drawStem) { ctx.moveTo(g.anchor, lo); ctx.lineTo(g.anchor, hi); }
    ctx.moveTo(g.anchor - g.capHalf, lo); ctx.lineTo(g.anchor + g.capHalf, lo);
    ctx.moveTo(g.anchor - g.capHalf, hi); ctx.lineTo(g.anchor + g.capHalf, hi);
    ctx.stroke();
  }
  return;
}
```
(Alternatively, delete the vertical branch — pick `el.horizontal`/indexAxis
`'y'` only and skip otherwise — so the plugin never claims an orientation
it does not draw.)

### WR-02: Scatter whiskers mix units — raw-metric std drawn on a weighted-score/rank axis, with a tooltip label that invites misreading

**File:** `dnallm-mark/js/main.js:279` (payload), `dnallm-mark/js/main.js:343-374` (y axis + tooltip), `dnallm-mark/js/error-bars.js:137-161` (point mode)
**Issue:** The per-model `performance.std` is the mean of per-task
**raw-metric** population stds (typically 0..1 metric units), but the
scatter draws it as ± whiskers around `weighted_score` (a normalized
z-score mean) or `rank_score` (rank points). On the default weighted view a
viewer reads the whisker as "the weighted score is 0.26 ± 0.09" — an
assertion the number cannot support; on the rank view a ~0.09-point
whisker on a 0..300 axis is visually meaningless. The tooltip line
`Seed spread: ±0.0891 (n=3)` sits directly beneath
`Weighted Score: 0.2617`, reinforcing the misreading. The planner ruled
this propagation acceptable (17-RESEARCH Q1: "whiskers drawn on y even
though y is rank-derived — **document that the whisker quantifies
raw-score seed spread**"), and `docs/METHODOLOGY.md` does document it — but
the user-facing chart text carries no such qualification, and the project's
core value is that public numbers are interpreted correctly. This is
display-only (no ranking or data impact), hence WARNING, not BLOCKER.
**Fix:** At minimum, make the tooltip self-qualifying per the research
note's own wording:
```js
if (typeof m.performance?.std === 'number') {
  lines.push(
    `Raw-score seed spread: ±${p.std.toFixed(4)}` +
    `${typeof p.n_seeds === 'number' ? ' (n=' + p.n_seeds + ')' : ''}`
  );
}
```
Consider also an axis-title or legend annotation ("whiskers: mean per-task
raw-metric seed spread, display-only"), or gating scatter whiskers off
until a corpus-wide multi-seed regeneration exists (the research's stated
alternative).

## Info

### IN-01: METRIC_MAP diverges from the exporter's legacy metric table (MSE/MAE uppercase)

**File:** `dnallm-mark/js/task.js:103-111` vs `script/export_runs.py:416-422`
**Issue:** The exporter's `LEGACY_DATASET_METRIC` accepts uppercase
`F1/MCC/MSE/MAE/R2`; the JS `METRIC_MAP` covers `F1/MCC/R2`
(+ AUPRC/AUROC/pearsonr/spearmanr) but not `MSE`/`MAE`. If a future
dataset declares `metric: "MSE"`, the exporter emits the trio
(`primary_slot` resolves to `mse`) but the task page's gating
`actualMetricKey === primaryKey` compares `'mse' !== 'MSE'` and the display
trio silently never renders — data present, display absent, no error. No
live impact today (the registry declares only `AUPRC/f1/mcc/spearmanr/r2`,
all of which both maps resolve identically — verified).
**Fix:** Add `MSE: 'mse'` and `MAE: 'mae'` to `METRIC_MAP` (or generate the
JS map from the exporter table to keep one authority).

### IN-02: Trio recording is independent of the raw-score presence gate

**File:** `script/summarize_comparison.py:579-592`
**Issue:** `load_model_inputs` records `std`/`n_seeds` from a datasetEntry
regardless of whether that entry's primary-metric **score** passed the
presence gate (`raw_score is None`), so a (hand-maintained) entry carrying
a trio but an absent metric value contributes its std to the per-model
display mean while contributing nothing to ranking/`samples` for that task.
The exporter cannot produce this shape (the trio requires ≥2 finite primary
values), so only hand-edited `model_performance` files can trigger it;
effect is display-only. 
**Fix:** For symmetry with the presence gate, record the trio only when
`raw_score is not None` (or document the tolerance for hand-edited inputs).

### IN-03: Floating bars can extend below the metric's natural domain (mean < std)

**File:** `dnallm-mark/js/task.js:394` + `dnallm-mark/js/error-bars.js:61-66`
**Issue:** `barDatum` returns `[mean - std, mean + std]`; for a small mean
with a larger std (e.g. mean 0.10, std 0.09 on a [0,1] metric) the bar —
not just a whisker — starts at −0.01 and the x axis auto-scales below zero,
visually implying an impossible negative metric. Does not trigger on the
current r2 data (std ≤ 0.089 vs means ≥ 0.58); inherent to the plan's
"native floating bars" choice and honest in the ±std sense.
**Fix:** Leave as-is (documented behavior), or clamp the bar's `lo` at the
metric's natural bound (e.g. 0 for rates) while keeping the cap honest —
only worth doing if real multi-seed data ever exhibits mean < std.
