13 — Dynamic dispatch core (动态调度核心)

Goal

The orchestrator dispatches (model×dataset×seed) cells as a work queue over per-GPU workers with worker-independent cell outputs, an exactly-once claim ledger, and resume semantics proven under mid-cell kill — legacy static sharding coexists behind explicit mode declaration. ( ROADMAP.md, Phase 13 Goal — requirements MGPU-01, MGPU-02, MGPU-06 )

What Shipped

  • A new sibling engine pipeline/dispatch_core.py (lazy-imported by run_sweep_shard.py behind --mode {static,dispatch}): deterministic enumeration → zero-cell refusal → lock → dispatch_state.json evidence → O_EXCL claim ledger (dispatch_ledger/) → spawn → finalize; the static path stayed byte-identical with the 49-test shard suite as the tripwire. (13-01-SUMMARY.md)
  • Dry-run plan artifact (the static projection verbatim plus one orchestrator_mode: "dispatch" marker), evidence-based merge refusal (dispatch roots need no merge), static byte-identity pins, and the Makefile lint slot. (13-02-SUMMARY.md)
  • Code-review hardening with mutation-proven pins: CR-01 --from-failures honored in dispatch mode, CR-02 lock create-to-write grace, CR-03 child pid persisted before wait, CR-04 per-cell containment; WR-01/02/03 claim-ledger guards. (STATE.md, Phase 13 decisions)

Evidence

  • Verification score: 23/23 must-haves verified, status: passed (.planning/phases/13-dynamic-dispatch-core/13-VERIFICATION.md frontmatter, verified 2026-10-20).
  • Suite: tests/test_dispatch_core.py + tests/test_sweep_shard.py — 102 passed in 1.42s (13-VERIFICATION.md:162), including the SC2 acceptance test test_sc2_kill_test_resume_exactly_once (a worker killed mid-cell and relaunched completes every cell exactly once — “green in this pass's 102/102 run”, 13-VERIFICATION.md:54) and the dry-run byte-identity tests (test_dispatch_dry_run_is_byte_identical_across_runs).
  • The frozen protocol order, claim naming (percent-encoded fields + sha256[:12] digest suffix), and stale-lock reclaim by pid-liveness are pinned in the module docstring of pipeline/dispatch_core.py and cited by 13-VERIFICATION truths 9-21.

Analysis

The hard problem was exactly-once execution under crash: a dispatcher killed mid-cell must never double-run or lose a cell on relaunch. Phase 13 solved it structurally — the O_EXCL claim ledger makes double-claim impossible by construction, resume is pure per-cell relaunch_decision over on-disk evidence (trainer_state marker or completed claim with agreeing cell key), and the SC2 kill test proves the property from the disk state alone rather than from orchestrator memory. The cost of that discipline appeared later as a genuine gap: dispatch roots initially carried no run_record.json (Phase 13 decision A3 deferred it), which surfaced as the 15-01 halt and was closed by 15-04 (see Gap Closures).

14 — Orchestration view & failure recovery (编排运行视图与失败恢复)

Goal

Running multi-GPU sweeps are observable (terminal table + machine-readable state file) and recoverable (cross-worker failure re-run with lane context; post-merge verify + confirm-gated cleanup). ( ROADMAP.md, Phase 14 Goal — requirements MGPU-03, MGPU-04, MGPU-05 )

What Shipped

  • dispatch_state.json frozen at consumer schema v2 (schemas/dispatch_state.json, strict draft 2020-12) — queue depth derived at publish under the state lock, per-worker in-flight cells, bounded failures list — plus the live plain-line terminal table rendered inside dispatch_core.py at the _write_state choke point. (14-01-SUMMARY.md)
  • export_runs.py --dry-run consumption seam and the --cleanup sibling mode: dual verification before any removal, behind a typed-phrase gate (the resolved --output-root string, exact equality); dispatch roots refuse merge by evidence. (14-02-SUMMARY.md)
  • Ledger-driven cross-worker failure re-run: --rerun-failed replays the claim-time lane verbatim (peft lane preserved — the 12-04 lane-blindness fixed), with append-only archive genealogy (dispatch_ledger/archive/ + rerun_of) and per-cell heterogeneous-lane refusal. (14-03-SUMMARY.md)

Evidence

  • Verification score: 28/28 must-haves verified, status: passed (.planning/phases/14-orchestration-view-recovery/14-VERIFICATION.md frontmatter, verified 2026-10-20).
  • Suite growth over the Phase-13 baseline: 66 dispatch tests at 14-01, 93 dispatch tests / 155 dispatch+shard combined at 14-03 (ROADMAP.md, Phase 14 plan rows); the flush property was proven on real lanes — a pty test reads the first [Dispatch] header within 3 s while a 5 s-holding fake cell keeps the drain alive (STATE.md, 14-01 decisions).
  • Named pins: the schema consumer test over schemas/dispatch_state.json, the D14-15 end-to-end (one command re-runs exactly the failed cells with byte-identical lane argv), and the typed-phrase cleanup refusal paths — all in tests/test_dispatch_core.py / tests/test_export_runs.py.

Analysis

The hard problem was observability that can never kill the run: the live table renders inside the single-writer state lock at the write choke point, so every rendered line corresponds to a committed state file — and the renderer's output errors are swallowed by contract, because a dying view must never fail a cell. The companion problem was trustworthy recovery: re-running failures verbatim required capturing the full lane (model, task, seed, fraction, peft, variant flags) at claim time — before anyone knew a cell would fail — which is why the ledger stores the lane in the claim itself and the re-run is a replay, never a re-derivation.

§ Gap closures

Two gaps that Phase 15's real-chain validation surfaced, both closed by dedicated plans with the maintainer's ruling. They are the milestone's clearest evidence that running the real thing finds what unit tests cannot.

15-04 — dispatch roots carry run_record.json

Gap: Phase 13 decision A3 deferred run records on dispatch roots — the dispatcher wrote cells, ledger, and state, but no run_record.json, so the export/consumption chain saw nothing. This halted 15-01 at the consumption dry-run criterion: the sweep was green, the chain empty.

Closure: dispatch_core.py now writes run_record.json for every cell it runs (completed or failed) at claim finalize — composed from the cell's own final_metrics.json plus the claim-time lane through run_sweep's own _new_record (the single record-schema authority), with WR-12 no-overwrite refusal and CR-04-routed failures. The fresh 2-cell smoke re-run then passed all four D15-02 criteria incl. “[Dry-run] 2 run record(s) across 1 model(s) / 1 task(s)”. (15-04-SUMMARY.md; supersession of Phase 13 A3 at its deferred handoff point)

15-05 — eval metrics reach final_metrics.json (WINDOWS #45)

Gap: run_finetune.py called bare trainer.evaluate() and discarded the result — faithful to the port since the Phase-7 deletion, so eval scores survived only inside trainer_state log_history. The first 12-cell sweep exported empty score slots; summarize emitted {} and skipped every species file. The consumption proof halted (D15-04), the remediation was routed to the maintainer (every option touched frozen, test-pinned contracts), and the ruling was option A: a deliberate narrow unfreeze of the producer.

Closure: run_finetune captures eval_results = trainer.evaluate() outside the rank guard and merges flat-additive merged = {**eval_results, **metrics} into final_metrics.json, with the write order final_metrics(v1) < flops < evaluate < merged re-write < marker copy (D-05 hardware reads stay pre-evaluate; WR-13 marker-last strengthened). Tier-1 pins updated, not weakened (contracts 76 green). The fresh-root re-run then carried eval_f1 in all 12 final_metrics and run_records, and the zero-modification chain emitted non-empty comparison files — WINDOWS #45 closed. (15-05-SUMMARY.md; the green re-run in 15-03-SUMMARY.md:127-218)
